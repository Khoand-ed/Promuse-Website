# Promuse landing page — architecture

How the site is built. What it shows is in `SPEC.md`; the HTTP contract is in `API.md`.

## 1. Overview

```text
Browser ──(static pages)─────────▶ Vercel · Next.js 16
   │                                 ├─ /[locale], /[locale]/privacy   static per locale, built from content/
   │                                 ├─ /auth/callback                 OAuth code exchange
   │                                 └─ /api/v1/*                      route handlers → services ──(RPC as the user)──▶ Supabase Postgres (RLS)
   └──(Google sign-in, PKCE)───────▶ Supabase Auth ◀──▶ Google OAuth

Game .NET backend (future, section 17) ┄┄ server-to-server, not built in v1 ┄┄▶ /api/v1/integrations/…
```

- The pages are static per locale and served from Vercel's CDN. Interactive parts are client islands.
- All copy, data and image slots come from `content/` (section 16), validated at build time.
- The browser signs in with Google through Supabase Auth. The session lives in cookies managed by `@supabase/ssr`.
- `/api/v1` is the only way a client reads or changes data. The game does not call it; the planned server-to-server link is in section 17.
- Postgres enforces ownership: row-level security for reads, `security definer` functions for writes. The app holds no secret key.

## 2. Stack

| Concern | Choice | Why |
|---|---|---|
| Framework | Next.js 16 (App Router), TypeScript strict, Node.js 24 LTS | Static pages and API routes in one codebase, room for more pages later |
| Styling | Tailwind CSS v4 | Tokens in CSS, fast iteration |
| Motion | GSAP (ScrollTrigger, SplitText), Lenis | Scroll-driven timelines and text effects for a P3R-level page |
| Languages | next-intl | Locale routing, static rendering per locale, typed messages from `content/text` |
| Content | JSON in `content/`, validated with zod; JSON Schemas generated from the same schemas | The owner edits content without code; a bad edit fails the check, not the page |
| Auth and data | Supabase: Auth with Google, Postgres | Free plan; RLS; independent of the game's backend |
| Validation | zod | One way to validate API input, environment and content |
| Tests | Vitest, Playwright | Unit tests for content, services and handlers; end-to-end tests in mock mode |
| Hosting | Vercel Hobby | Free for personal projects; a preview for every branch |

## 5. Layers

```text
content/*.json ─▶ src/content (zod loaders) ─▶ section components (Server Components) ─▶ client islands (motion, modals, reward widget)

UI component ─▶ RewardGateway (browser) ─▶ fetch /api/v1/* ─▶ route handler ─▶ service interface ─▶ Supabase implementation ─▶ Postgres function or RLS read
```

- Everything under `src/server/` imports `server-only`.
- Components never import JSON from `content/`; they receive typed, validated objects from `src/content/`.
- Route handlers parse input with zod, call `requireUser()`, call one service method and map its result to HTTP as `API.md` says. No business logic in handlers.
- Services return typed results (discriminated unions) for expected outcomes. Only unexpected failures throw; the handler turns them into `internal`.

### Server services

```ts
// src/server/services/types.ts
export type Locale = 'vi' | 'en';

export interface UserContext {
  userId: string;
}

export interface PreregistrationService {
  getStatus(user: UserContext): Promise<
    { registered: false } | { registered: true; registeredAt: string; campaignKey: string }
  >;
  register(user: UserContext, locale: Locale): Promise<
    | { status: 'created' | 'existing'; registeredAt: string; campaignKey: string }
    | { status: 'campaign_closed' }
  >;
}
```

- `createSupabaseServices(db)` builds the services for one request from a user-scoped Supabase client, so every query runs as that user and RLS and `auth.uid()` apply.
- `createMemoryServices(seed)` builds in-memory versions with the same behaviour for unit tests.

### Browser reward gateway

```ts
// src/lib/reward/types.ts
export type PreregStatus =
  | { kind: 'signedOut' }
  | { kind: 'signedIn'; email: string; registered: false }
  | { kind: 'signedIn'; email: string; registered: true; registeredAt: string };

export interface RewardGateway {
  getStatus(): Promise<PreregStatus>;
  signIn(returnPath: string): Promise<void>; // leaves the page for Google
  signOut(): Promise<void>;
  register(locale: Locale): Promise<
    { status: 'created' | 'existing'; registeredAt: string } | { status: 'campaign_closed' }
  >; // throws on network or server errors
}
```

- `SupabaseRewardGateway`: Supabase browser auth plus `fetch` to `/api/v1/preregistration`.
- `MockRewardGateway` (`src/lib/reward/mock.ts`): no network, for development and previews. `?mock=` picks a scenario; the scenario and a fake account (`nguoi.choi@example.com`) live in `sessionStorage` (`promuse:mock`), so they survive the fake trip to Google, which waits 800 ms and reloads the page at the return path, as the real one would. A `?mock=` value that differs from the saved one starts over.

  | `?mock=` | Starts | The button leads to |
  |---|---|---|
  | `signed-out` (default) | signed out | sign-in, then `created` → `registered` |
  | `signed-in` | signed in, not registered | `created` → `registered` |
  | `registered` | signed in, registered on 2026-11-01 | — (`alreadyRegistered`) |
  | `existing` | signed out | sign-in, then `existing` → `alreadyRegistered` |
  | `cancelled` | signed out | back with `auth=cancelled` → `signedOut` with the notice |
  | `error` | signed in | a failure → `error`, every retry fails again |
  | `closed` | signed in | `campaign_closed` → `closed` |

- The reward widget is `src/components/sections/RewardActions.tsx` over the pure state machine in `src/lib/reward/machine.ts` (`reduce`, `popupAllowed`), so the rules are unit-tested without a browser.
- `NEXT_PUBLIC_BACKEND_MODE` chooses the gateway: `off` (no gateway; the widget shows `notOpen`), `mock` or `supabase`. The reward widget is a state machine over this interface and holds no Supabase code. Swapping the backend later means a new gateway and service implementation, not a new widget.

## 6. Rendering

- `src/app/[locale]/page.tsx` and `privacy/page.tsx` render statically for each locale (`generateStaticParams` and `setRequestLocale`). Page code never reads cookies or headers, which keeps it static.
- Content is read and validated at build time; editing content means a rebuild, which Vercel runs on every push.
- Cache Components (`cacheComponents`, `partialPrefetching`) stays off, although `create-next-app` turns it on: every page is static and needs no per-request data. Revisit when Next.js makes it the default.
- Sections are Server Components that receive typed content. Motion wrappers, modals, sliders and the reward widget are client components.
- Heavy client code (Supabase client, modals, sliders) loads with `next/dynamic` or on first interaction.
- The reward widget asks the gateway for status after mount; the static HTML shows the sign-in button disabled until then, or `notOpen` in `off` mode.

## 7. Authentication

### Web sign-in (PKCE)

1. The widget calls `gateway.signIn('/en?intent=prereg')` (the current locale path), which calls `supabase.auth.signInWithOAuth({ provider: 'google', options: { redirectTo: location.origin + '/auth/callback?next=' + encodeURIComponent(path) } })`.
2. Google returns to Supabase, which redirects to `/auth/callback?code=…&next=…`.
3. `src/app/auth/callback/route.ts`: if the URL has `error` (the visitor cancelled), redirect to `next` with `auth=cancelled`; otherwise call `exchangeCodeForSession(code)` and redirect to `next`, or to `next` with `auth=error` on failure. Only relative `next` values are accepted; anything else becomes `/`.
4. The page loads. The widget sees a session and `intent=prereg`, scrolls to `#reward`, calls `POST /api/v1/preregistration`, shows the result, then removes `intent` from the URL with `history.replaceState`.

### Session handling

- Browser: `createBrowserClient(NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY)`.
- Server: `createServerClient` with Next.js cookies.
- `src/proxy.ts` refreshes the session with `getClaims()` and writes refreshed cookies, as in the Supabase guide for Next.js.

### API authentication: `requireUser(request)`

1. If `Authorization: Bearer <token>` is present, create a client that sends that header and verify the token with `getClaims(token)`. This serves curl tests (`/dev/token`) and future first-party clients.
2. Otherwise use the cookie-based server client and `getClaims()`.
3. On failure, respond `401 unauthorized`.
4. Return `{ user: { userId }, db }`, where `db` sends the user's JWT so RLS and `auth.uid()` apply.

The game does not use this sign-in; see section 17.

## 8. Proxy

```text
request ─▶ next-intl middleware (locale routing) ─▶ response
        └▶ Supabase session refresh on that same response (getClaims, set cookies)
```

- One `src/proxy.ts`, composed of `createMiddleware(routing)` and the Supabase refresh helper in `src/lib/supabase/proxy.ts`.
- Matcher: skip `api`, `auth`, `dev`, `_next`, `_vercel` and any path with a dot. Route handlers refresh their own session.
- Skip the Supabase step when the request carries no Supabase auth cookie.

## 9. Data model

`supabase/migrations/0001_init.sql`:

```sql
create table public.campaigns (
  key        text primary key,                          -- 'prereg-launch'
  kind       text not null check (kind in ('preregistration')),
  title      jsonb not null,                            -- {"vi": "...", "en": "..."}, for admin views
  rewards    jsonb not null,                            -- [{"type": "gacha_currency", "amount": 1800}]
  starts_at  timestamptz not null default now(),
  ends_at    timestamptz                                -- null: open-ended
);

create table public.preregistrations (
  user_id      uuid not null references auth.users (id) on delete cascade,
  campaign_key text not null references public.campaigns (key),
  email        text not null,
  google_sub   text not null,                           -- Google account id: the key the game uses later (section 17)
  locale       text not null check (locale in ('vi', 'en')),
  created_at   timestamptz not null default now(),
  primary key (user_id, campaign_key),
  unique (google_sub, campaign_key)
);

alter table public.campaigns        enable row level security;
alter table public.preregistrations enable row level security;

create policy "read own preregistrations" on public.preregistrations
  for select to authenticated using (user_id = (select auth.uid()));

-- No insert, update or delete policies: writes go through the function below.
revoke insert, update, delete on public.campaigns, public.preregistrations
  from anon, authenticated;
```

- `rewards[].type` is an internal key, not a display name. The future integration maps it to a game item (section 17).
- The privacy page (`SPEC.md`, section 13) lists exactly the personal fields stored here: `email`, `google_sub`, `locale`, `campaign_key`, `created_at`. Keep the two in sync.

### Function

`language plpgsql`, `security definer`, `set search_path = ''` (fully qualified names inside), and executable only by `authenticated`:

```sql
revoke all on function public.register_preregistration(text) from public, anon;
grant execute on function public.register_preregistration(text) to authenticated;
```

`register_preregistration(p_locale text) returns jsonb`

1. `auth.uid()` is null → raise an exception.
2. `p_locale` is not `vi` or `en` → raise an exception (the API validates first).
3. Take the latest campaign of kind `preregistration` by `starts_at`. None → `{"status": "campaign_closed"}`.
4. The user already has a registration for it → `{"status": "existing", "registeredAt": …, "campaignKey": …}`.
5. The campaign is outside its window (`starts_at > now()` or `ends_at <= now()`) → `{"status": "campaign_closed"}`.
6. Insert the registration with `on conflict do nothing`. Read the email from `auth.users` and the Google account id from `auth.identities` (`provider = 'google'`, column `provider_id`); if either is missing, raise an exception. → `{"status": "created", …}`. If a parallel request won the insert, return `existing`.

### Campaign data

`supabase/migrations/0002_prereg_campaign.sql` (a migration, not `seed.sql`, so production gets the row too):

## 12. Testing

- Unit (Vitest): content schemas and loaders against valid and broken samples; the `check:content` rules (locale parity, placeholder parity, image slots); services against the in-memory implementations; route handlers against fake services (status codes and envelopes); zod schemas; the reward widget's state machine against `MockRewardGateway`.
- End-to-end (Playwright, `NEXT_PUBLIC_BACKEND_MODE=mock`): both locales load; modals work by keyboard; deep links; every `?mock=` scenario; motion off via `page.emulateMedia({ reducedMotion: 'reduce' })`.
- Manual (P3): two real Google accounts, plus `curl` against the API with an access token from `/dev/token`.

## 16. Content system

```text
content/
├─ text/
│  ├─ vi.json            every visible string, grouped by block: common, nav, intro, hero, reward, story,
│  └─ en.json            features, gameplay, characters, footer, privacy — the same keys in both files
├─ data/
│  ├─ site.json          BPM, trailer id, social and store links, platforms with status, copyright holder, logo slot
│  ├─ hero.json          key visual slots (desktop, mobile) and optional layers
│  ├─ reward.json        reward art slot
│  ├─ story.json         image slot, number of slogan bands
│  ├─ features.json      cards and tabs: order and image slots
│  ├─ gameplay.json      tabs: order, slider image slots, gacha rates
│  └─ characters.json    order, id, slug, name, rarity, stats, theme colour, image slots
└─ schemas/              generated from the zod schemas; never edited by hand
```

- Keys are dotted paths by block (`hero.status`, `characters.items.nova.tagline`). Characters are keyed by slug, never by position.
- Every file — text and data — starts with `"$schema"` pointing at its generated schema, so VS Code shows what each field means (in Vietnamese, for the owner) and underlines invalid values. The text loader drops `$schema` before handing the messages to next-intl.
- An image slot is `{ "src": "/images/…", "width": 1280, "height": 720, "alt": "<text key>" }`. The build checks whether the file exists under `public/`; when it does not, `ImageSlot` renders a labelled placeholder with the same aspect ratio.
- Markers: `[TODO] <what to write>` for missing text; `[REVIEW]` for drafts and translations waiting for the owner; `null` for a data value not decided yet (a theme colour, the copyright holder). All of them show up in the report, and text markers show on the page, so nothing ships unnoticed.
- `npm run check:content` validates every file against its schema; checks that both locales have the same keys and the same ICU placeholders (`{email}`, `{date}`); lists missing images and file-convention assets (`opengraph-image.png`, `icon.png`); regenerates `content/schemas/`; and writes `CONTENT_TODO.md`. Each entry gives the file, the key, the line, what is needed, how to fill it and where it shows on the page. The check fails on invalid content, never on a TODO.
- `src/content/` holds the zod schemas (the single source for validation and for the JSON Schemas) and the loaders. Components use the loaders only.
- `doc/CONTENT_GUIDE.md`, in Vietnamese, is the owner's how-to: editing text, replacing images, previewing, running the check.

## 17. Game integration (future, not built in v1)

The game has its own accounts (guest, or username and password), its own Postgres and its own Mailbox. It has no Google sign-in yet. The planned link, built only when the owner asks:

1. The game's .NET backend adds Google sign-in or account linking and verifies Google ID tokens itself. It does not use Supabase.
2. When a game account has a Google account id (`sub`), the .NET backend calls a server-to-server endpoint on this site — for example `POST /api/v1/integrations/game/preregistration-claims` with `{ "googleSub": "…" }` — authenticated with a secret the two servers share.
3. The site answers whether that Google account pre-registered and with which rewards, and records the claim exactly once per account and campaign; a repeated call returns the same answer.
4. The .NET backend sends the reward through its own Mailbox, mapping `rewards[].type` to its item ids.

What this means for the site:

- v1 already stores `google_sub` with every registration, so nothing has to be collected again.
- The integration adds one migration (claim columns or a claims table), one route, one service method and one server-only secret. How the site writes the claim without a service-role key (for example a dedicated Postgres role, or a function guarded by the secret) is decided then, and `AGENTS.md` gets an explicit exception for that secret.
- The site never calls the game backend, and the game never reads this database.
